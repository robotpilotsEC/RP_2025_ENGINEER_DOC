队列互斥量和信号量（Queues mutexes and semaphores）

## 队列（Queues）
队列是任务间通信的主要形式。它们可用于在**任务之间**以及**中断和任务之间**发送消息。在大多数情况下，它们用作线程安全的 FIFO（先进先出）缓冲区

FreeRTOS的队列选择将**数据本身**复制传输，而**不是通过引用**的办法：

- 无需发送任务或者接收任务判断消息的分配和释放
- 通过定义队列，发送包含**消息**及其**大小**的信息实现任务间**可变大小消息**传递
- 同样可以通过队列实现接收来自不同对象的不同类型消息

~~~
[发送任务] 
   |
   v
[构造消息结构体: type + data指针]
   |
   v
[xQueueSend发送到队列]
   |
   v
[队列]
   |
   v
[接收任务]
   |
   v
[xQueueReceive接收消息]
   |
   v
[根据type解释data内容并处理]
~~~

## 队列阻塞
- 当任务尝试从空队列读取或者写入已满队列时，任务将会进入 `Blocked`状态，等待队列数据可以读取

## 二进制信号量（Binary Semaphores）
**二进制信号量用于互斥和同步目的**

- 二进制信号量和互斥量非常相似，但有一些细微的区别：互斥量包含**优先级继承机制**，而二进制信号量则没有。这使得二进制信号量成为实现同步（任务之间或任务与中断之间）的更好选择，而互斥体是实现简单互斥的更好选择
- 将二进制信号量视为只能容纳一个对象的队列，只有 `空` 和 `满`两种情况（二进制），因此中断和任务只关心队列**状态**，不关心内容，以此**实现同步**
- 具体来看，任务不断去读信号量，而外设中断不断等待触发事件，发出信号量，使中断和任务达成同步。

示例：
~~~
#define LONG_TIME 0xffff
#define TICKS_TO_WAIT 10

SemaphoreHandle_t xSemaphore = NULL;

/* Repetitive task. */
void vATask( void * pvParameters )
{
    /* We are using the semaphore for synchronisation so we create a binary
       semaphore rather than a mutex. We must make sure that the interrupt
       does not attempt to use the semaphore before it is created! */
    xSemaphore = xSemaphoreCreateBinary();

    for( ;; )
    {
        /* We want this task to run every 10 ticks of a timer. The semaphore
           was created before this task was started.

           Block waiting for the semaphore to become available. */
        if( xSemaphoreTake( xSemaphore, LONG\_TIME ) == pdTRUE )
        {
            /* It is time to execute. */

             ...

            /* We have finished our task. Return to the top of the loop where
               we will block on the semaphore until it is time to execute
               again. Note when using the semaphore for synchronisation with an
               ISR in this manner there is no need to 'give' the semaphore
               back. */
        }
    }
}

/* Timer ISR */
void vTimerISR( void * pvParameters )
{
static unsigned char ucLocalTickCount = 0;
BaseType_t xHigherPriorityTaskWoken = pdFALSE;

    /* A timer tick has occurred. */

    ... Do other time functions.

    /* Is it time for vATask() to run? */
    xHigherPriorityTaskWoken = pdFALSE;
    ucLocalTickCount++;
    if( ucLocalTickCount >= TICKS_TO_WAIT )
    {
        /* Unblock the task by releasing the semaphore. */
        xSemaphoreGiveFromISR( xSemaphore, &xHigherPriorityTaskWoken );

        /* Reset the count so we release the semaphore again in 10 ticks
           time. */
        ucLocalTickCount = 0;
    }

    /* Yield if xHigherPriorityTaskWoken is true. The 
       actual macro used here is port specific. */
    portYIELD_FROM_ISR( xHigherPriorityTaskWoken );
}

~~~

## 计数信号量（Counting Semaphores）
**计数信号量可以被认为是长度大于 1 的队列。同样，信号量的用户对存储在队列中的数据不感兴趣 - 只是队列是否为空**

共两个作用：
- 计算事件数：`发生事件`提供信号量（*递增信号量计数*值），而`处理程序`获取信号量（*递减信号量计数值*），所以**计数值是已发生的事件数与已处理的事件数之间的差值**
- 资源管理：任务首先获取资源信号量(*递减信号量计数值*),当计数值为0时，则代表**无可用资源**

## 互斥量（Mutexes）
**互斥量是实现简单互斥的更好实现，也是实现多任务间共享资源的更好实现**
- **互斥锁（mutual exclusion）** 的作用类似于 `token`，当任务希望访问某个资源时，他必须先获得 `token`，任务对资源处理后，需要返还 `token`
- 互斥量和信号量的API几乎相同，`xSemaphoreTake()`、`xSemaphoreGive()`，都可以设置阻塞时间
- 互斥量保留了**优先级继承机制**
- 中断**不能阻塞等待**由互斥量保护的资源

### 优先级继承：
- 假设有两个任务：高优先级任务A，低优先级任务B。
- 低优先级任务B先获得了 `mutex`，并且还没释放。
- 高优先级任务A也要这个 `mutex`，但发现被占用，所以阻塞（Blocked）。
- 这时，FreeRTOS 会自动把持有 `mutex` 的低优先级任务B 的**优先级提升**到和高优先级任务A 一样高。
- 这样，B 会更快地获得 CPU 时间片，尽快完成任务并释放 `mutex`。
- 一旦 `mutex` 被释放，B 的优先级会恢复到原本的低优先级
~~~
[低优先级任务获取mutex]
   |
   v
[高优先级任务请求mutex，被阻塞]
   |
   v
[低优先级任务临时提升到高优先级]
   |
   v
[低优先级任务释放mutex]
   |
   v
[高优先级任务获得mutex]
   |
   v
[低优先级任务恢复原优先级]
~~~
***
### FreeRTOS 实现了一种基本的优先级继承机制，旨在优化空间和执行周期
- 任务优先级将会提高到：该任务**已有互斥量**但是被更高优先级的任务所申请的**相同优先级**
- 任务将保持最高优先级，直到**所有互斥量释放**，与释放顺序无关
- 本任务继承高优先级后，不会因为**原本高优先级任务访问超时**或者**删除**而导致本任务优先级的降低

~~~
[低优先级任务A持有mutex1]
   |
   v
[高优先级任务B请求mutex1, A提升到B的优先级]
   |
   v
[A持有mutex2]
   |
   v
[更高优先级任务C请求mutex2, A提升到C的优先级]
   |
   v
[A释放mutex2, 若还有高优先级任务等mutex1, 保持当前提升优先级]
   |
   v
[A释放所有mutex, 恢复原始优先级]
~~~
